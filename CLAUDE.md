# СБОРКА — маркетплейс сборки мебели (Якутск)

Контекст для Claude, работающего над этим проектом на сервере. Читай целиком перед первой правкой.

## Что это

Веб-платформа (сайт + PWA) для заказа сборки мебели в Якутске. Клиент считает стоимость в калькуляторе и оставляет заявку, мастера откликаются ценой, клиент выбирает по цене и рейтингу. Платформа берёт комиссию 30%. Первая категория — сборка мебели, дальше горизонтально: сантехники, электрики, муж на час.

Полная концепция — `docs/concept.md`. Дорожная карта — `docs/roadmap.md`. Готовый кликабельный макет всех экранов — `reference/mockup.html` (это эталон дизайна и логики, открой в браузере).

## Стек (рекомендация — адаптируй под реальный сервер)

- **Фронт**: папка `public/` (`index.html` + `css/app.css` + `js/app.js`), все экраны свёрстаны. НЕ пересобирать и не заменять фреймворком. Правки — строго по дизайн-системе (см. «ГЛАВНОЕ ПРАВИЛО» выше), не «с нуля на глаз».
- **Бэк**: Node.js (Fastify/Express) или Cloudflare Workers — по тому, что стоит на сервере.
- **БД**: PostgreSQL (Neon или локальный на сервере).
- **Уведомления**: абстракция каналов `notify(user, msg)` → WhatsApp (Green API) первым, Max и SMS добавляются без переделки. SMS — обязательный запасной канал.
- **Вход**: клиент — без регистрации (заявка с именем + телефоном); мастер — простой логин (кабинет, отклики, рейтинг). SMS-верификацию НЕ вводим на старте.

Первым делом уточни у Богдана фактические параметры сервера (ОС, что установлено, домен) и подстрой стек — не начинай ставить окружение вслепую.

## Ключевые продуктовые правила (не нарушать)

1. **Не чистый аукцион.** Клиент ставит бюджет-ориентир, калькулятор подсказывает вилку, мастера откликаются ценой + рейтингом. Клиент выбирает лучшего в бюджете, не самого дешёвого. Гонку на дно не строим.
2. **Чат и оплата — через платформу.** Иначе мастера уводят клиентов, и платформа умирает. На старте номера могут быть видны (живём на потоке), но архитектуру закладывать под маскировку контактов.
3. **Калькулятор поднимает чек** — допы встроены в расчёт, вилка «от–до», считает по внутреннему прайсу, наружу только вилка.
4. **Партнёрская атрибуция** — ссылки вида `?ref=uyut`, источник фиксируется за клиентом, магазин получает комиссию.

## Структура фронта (public/)

- `index.html` — клиентский флоу: калькулятор → детали заявки → отклики мастеров → экран сделки со статус-трекером. Экраны переключаются по атрибуту `data-role` / `data-cview` (сейчас через демо-навигацию — при интеграции разведёшь по роутам/состоянию).
- `css/app.css` — вся дизайн-система: токены (обе темы), кнопки, карточки, чипы, трекер, калькулятор. Единственный источник стиля. Переиспользуй эти классы, новых стилей не плоди.
- `js/app.js` — калькулятор (массивы `items`/`addons` с прайсом), навигация, портфолио. Прайс держи в синхроне с таблицей в этом файле.

Роли `master`, `partner`, `masterprofile`, `deal` в разметке — основа кабинетов мастера и партнёра; при интеграции вынеси в свои страницы/роуты, стиль бери из того же `app.css`.

Git-репозиторий — ЕДИНСТВЕННЫЙ источник правды о реальной версии продукта. Правки вносишь ты (и бэкенд, и фронт) и владелец напрямую; дизайн-Claude подключается точечно — согласование нового экрана/компонента или ревью постфактум (см. «ГЛАВНОЕ ПРАВИЛО» выше). Чтобы никто не работал по устаревшей копии:

1. **Перед началом любой работы — `git pull`.** Сначала подтяни реальную версию, потом правь. Иначе затрёшь чужие изменения.
2. **Любая правка = коммит.** Не закоммиченная правка невидима остальным и будет потеряна. Правишь — сразу коммить и пуш.
3. **Правки владельца напрямую на сервере — коммить немедленно** (с пометкой «правка владельца: …»), чтобы история их увидела.

5. **Конфликт при pull, если дизайн-Claude параллельно правил фронт — не затирай, разбирай вручную.**
